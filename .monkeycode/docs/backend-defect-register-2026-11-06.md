# 后端缺陷登记 2026-11-06

本册三条都来自"BOM 下线"这一产品决策的取证副产，但三条本身是现库既有缺陷，与 BOM 去留无关，BOM 不下线也必须修。行号均为本轮实读，非转述。

## D-57 生产完工扣料把批次维度折平，落流水的批次号取决于数据库返回顺序

现象（源码面，可指行）：backend/src/services/production_order_ops/completion.rs 第 353 到 376 行的私有装载函数 batch_load_stock_records 的返回类型是 HashMap<i32, inventory_stock::Model>，函数体先按 product_id 集合加默认仓库过滤取回全部库存行（带 lock_exclusive 行锁），末尾以 stocks.into_iter().map(|s| (s.product_id, s)).collect() 收成映射。而 backend/src/models/inventory_stock.rs 的 Model 有 33 列，库存行的区分维度是 warehouse_id、product_id、batch_no（第 35 行）、color_no（第 37 行）、dye_lot_no（第 39 行）、grade（第 41 行）的复合，不是 product_id 单维。

根因：把多维行集收成一维键的映射，同一物料在同一仓库里并存多个批次时，后写入的行覆盖先写入的行，每个物料只剩一行进入 stock_map。第 385 行的扣料循环再按 material_id 从这张映射里取行，于是每个物料只可能扣到那一行所代表的那个批次。

由此三条独立后果：

1 其余批次的库存量既不参与可用量判断也不被扣减，账面上"投了纱但没扣"，且不会报错。这是静默的数据错，不是可重试的失败。

2 第 480 到 483 行落 PRODUCTION_CONSUMPTION 流水时，batch_no、color_no、dye_lot_no、grade 四个追溯维度全部 clone 自那条随机存活的行。也就是说流水记录的"用了哪批纱"取决于数据库返回顺序，同一笔业务两次执行可以记出两个批次。这直接违反目标里"支持缸号、订单、客户追溯"与"批次可追溯"的要求，属功能级缺陷而非展示问题。按行业口径，纱批次是投料记录的一部分，必须是操作者声明的事实而不是查询副产。

3 余量校验也被折平：只拿那一行的 quantity_meters 与总消耗量比大小，多批次合计够而单批次不够时会误判不足，反之会放行本不该放行的投料。

修法方向（随 BOM 下线的同一条改造一起做，不另立方案）：扣料依据换成流转卡投纱明细后，扣料键必须升到 (material_id, batch_no) 双维，装载函数返回按物料加分批次的行集合而不是单键映射，逐批次扣减并逐批次落流水，行锁与批量装载（禁 N+1）的既有语义保留。

验收判据：同一生产订单同一物料跨两个批次投纱时，两条批次各自的库存行都发生扣减，且流水出现两条、batch_no 各等于投纱明细里声明的批次，不靠查询返回顺序取得。单批次合计够但单行不够的场景要能显式失败并给出可读原因。

## D-58 扣料计量口径只有米数一条，公斤按米折算，成品纱这类按重量计量的投入物没有正确口径

现象（源码面）：completion.rs 第 437 到 459 行的 calculate_deduct_qty 入参是 qty_before_meters、qty_before_kg、consumption_qty 三个 Decimal。函数体第 443 行只用 quantity_meters 与 consumption_qty 比大小判够不够，第 450 行按米相减得余米，第 452 到 455 行的公斤余量是 qty_before_kg - (qty_before_kg * consumption_qty / qty_before_meters)，即纯按比例折算，米数为零时第 455 行原样返回原公斤数。第 567 到 568 行确认这两个 before 值取自库存行的 quantity_meters（模型第 49 行）与 quantity_kg（模型第 52 行）。

根因：consumption_qty 只有一条来源，即第 388 行 bom_item.quantity 乘生产数量再 round_dp(4)，而 bom_items 的列集合（backend/src/models/bom_item.rs 第 12 到 22 行）只有 quantity 与 unit 两项，unit 是 Option<String> 且不参与任何分支判断。于是投入量的语义被隐式钉死成"米"，unit 只是一个不被消费的字符串。

后果：对以重量计量采购与存储的成品纱线，这条路径拿米数判库存是否够、按米扣减，公斤只是被等比例缩一下，不是按实际投料重量扣。第 455 行的分支还意味着：某个按公斤管理的纱线行米数为零时，米数校验形同不存在，扣料会放行并把公斤数原样保留，等于只落流水不动账。即便今天有人认真配好 BOM，成品纱的账也扣不正确。行业侧纱线的标识与计量口径是最小包装在公定回潮率下的净重加线密度（FZ/T 10008-2018 一类纱线标识标准），报价与成本核算一律以克或公斤为单位，本仓的扣料路径与该口径不接轨。

附带一条外显问题：第 391 到 396 行的失败文案是"原材料(ID=7)在默认仓库中无库存记录，无法扣减"，把内部主键 ID 直接打给使用者，属仓库成文规范禁止的"用户可见文案塞实现细节"。改造这条路径时新文案只能说该做什么（例如先为该物料登记批次库存或补录投纱），不得外显 ID 与列名。

修法方向：投入量必须带自己的计量单位并按单位分支校验，重量口径直接对 quantity_kg 相减，不允许用米数折算代替；缺单位或单位既非长度族也非重量族时显式拒绝。BOM 下线后该口径落到投纱明细的 unit 列，需要一份受控单位词表（与产品档案的交易计量单位同源，不新造第二套取值）。

待产品确认一条（不确认则本条按缺陷保留）：纱线在本系统的实际入库计量单位是公斤还是也有米数口径。若全部按公斤，则上面的米数校验对纱线族恒不成立，优先级高于 D-57。

## D-59 生产订单完工这条库存联动腿在 e2e 面上从未被验证过（存量漏测，转用例）

现象（取证口径两条，互不依赖）：全仓 frontend/e2e 检索 PRODUCTION_CONSUMPTION 命中 0 处；检索把生产订单推到 COMPLETED 的动作也没有命中，frontend/e2e/production/02-execute.spec.ts 第 54 行只把状态推到 IN_PROGRESS，frontend/e2e/flow/109-bpm-approval-depth.spec.ts 第 65 行出现的 COMPLETED 只是状态常量表的键定义，不是该域的推送。

后果：D-57 与 D-58 之所以长期无人发现，直接原因是这条腿没有用例覆盖。按目标里"功能未被测试覆盖即视为功能缺失"的口径，生产完工到原材料扣减到库存流水到成品入库这一整段属未验证面，不能因为它编译通过就当作已具备。同时它落入目标 C 节与 G 节点名的"新增入库单/出库单，保存后刷新，库存数与批次更新正确"这一要求，是应覆盖而未覆盖。

转化计划：与 BOM 下线同一条车道补 e2e，号段用 470 与 471（472 及以上未分配，落笔前再横扫一次在途车道的实际占用）。470 覆盖正向，登记两批次投纱后完工，断言两个批次各自的库存余量与两条流水的 batch_no 精确等于声明值；471 覆盖反向，投纱明细为空时完工被显式拒绝且库存与流水都不动。两条都要真断言，不许用 skip 或放宽期望换取通过；前置数据由本用例自建，不依赖库里恰好有行可用。
