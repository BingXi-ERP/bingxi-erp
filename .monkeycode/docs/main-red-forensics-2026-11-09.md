# 主线红取证 2026-11-09

## 结论一 flow16 红不是主干继承红，是同一份未修测试文件在六支里各带一份

主干顶点 6a0ca600e 的 frontend/e2e/flow 目录实测有 183 份 spec，其中 456-attachment-flow-and-print-data-chain、458-inventory-count-diff-and-transfer-persistence、461-purchase-receipt-to-ap-conservation 三份整档不存在（按 origin/main 树名清单与逐档行数双口径复核，两份口径互相独立，三份行数均为 0）。因此六支同时在 flow(16/20) 变红不构成"主干侧红"，只能是各支自带的副本自带破腿。

按 PR 头逐一取三枚破腿签名的实测结果如下。签名三处分别取 456 档的 long filename must 4xx 断言、458 档超量腿不带色号与缸号的明细字面量、461 档把已解析定标值回喂原始解析口那一行。

1. #1182 审计六维定位支，破腿签名 3。
2. #1183 超折扣审批门支，破腿签名 3。
3. #1184 BOM 与 MRP 下线支，破腿签名 3。

6. #1188 物流面单配对支，破腿签名 0（本支头 863e2a419 已修）。

六支 CI 面同刻实测，均为 90 枚 check-run 全收口，红面都含收尾清理与真实性门禁两枚汇总型 job。收尾清理是 if always 的 needs 聚合器，真实性门禁随分片红连带，两者不计入本支缺陷。摘掉这两枚之后，#1182 余 flow16 与 flow17，#1183 余 flow16 与 flow20，#1184 余 flow16，#1186 余 flow16，#1187 余 flow15 与 flow16。也就是说 flow16 六支同红由这三份重复文件解释，各支额外的 flow15、flow17、flow20 才是本支自己的红。

## 结论二 三条破腿各自的真实契约

1. 附件上传端点只用客户端原名的后缀做白名单，存盘名由服务端按供应商与资质两枚主键加后缀生成，原名既不入库也不进路径，落库列宽 500 且有双道长度门。因此 254 字符的合法 PDF 原名返回 200 是契约正确，4xx 断言的前提不成立。
2. 调拨建单期的可用量预检按产品、色号、批次、缸号四维匹配库存行；不传色号等于要求色号为空串，任何染色布库存行都匹配不上，于是三条负例腿全部以"无匹配库存"的名义被挡，其中负数量腿本该建单成功却拿到业务错误，用例当场失败。同域判定不对称这条缺口登记仍成立，该写路径无非负校验。
3. 十进制出参的线格式契约已在同腿的定标断言里校验过一次，派生量之间比对必须走"两个已解析定标值对平"的口，回喂原始解析口会拿字符串契约去判一个已解析对象，造出一条与被测对象无关的红。
