## 结论二 三条破腿各自的真实契约

1. 附件上传端点只用客户端原名的后缀做白名单，存盘名由服务端按供应商与资质两枚主键加后缀生成，原名既不入库也不进路径，落库列宽 500 且有双道长度门。因此 254 字符的合法 PDF 原名返回 200 是契约正确，4xx 断言的前提不成立。
2. 调拨建单期的可用量预检按产品、色号、批次、缸号四维匹配库存行；不传色号等于要求色号为空串，任何染色布库存行都匹配不上，于是三条负例腿全部以"无匹配库存"的名义被挡，其中负数量腿本该建单成功却拿到业务错误，用例当场失败。同域判定不对称这条缺口登记仍成立，该写路径无非负校验。
3. 十进制出参的线格式契约已在同腿的定标断言里校验过一次，派生量之间比对必须走"两个已解析定标值对平"的口，回喂原始解析口会拿字符串契约去判一个已解析对象，造出一条与被测对象无关的红。

## 结论四 模拟器 E2E 那枚红属环境型，不改工作流迁就

证据取自 job 129122217952 的全量日志（落盘 red-863e2a419-129122217952.log，79878 字节）。断言块为 0，无用例失败行，无 N failed 摘要。失败发生在 android-emulator-runner 这个 action 内部的启动轮询，不在工作流脚本里：对 sys.boot_completed 的探测共 167 次，自 11 时 05 分 39 秒至 11 时 13 分 09 秒约七分半，始终未取到 1，随后 action 自行 emu kill 并以退出码 224 判负。日志内无 emulator ERROR、无段错误，14 处 crash 字样均来自脚本里清空崩溃缓冲的命令文本而非真实崩溃。

同车道上一个头的同一 job 是通过的，故判为环境型 flaky（该执行体上模拟器在预算内未完成启动），不是源码缺陷也不是工作流逻辑缺陷。处置为随新头重跑观察，不动 android.yml 的启动预算或 API 级别去迁就单次慢启动；若连续多轮复现再按证据决定是否给启动预算或启用硬件加速。

注意口径：本支的收敛判据按 head 上全部 check-run 计，android.yml 的 job 也计入，因此这枚环境型红若再现，本支就不能报全绿，须如实登记而不是摘掉它凑绿。

## 结论五 新增用例改变分片分布，会把别处潜伏的夹具脆弱暴露成新红

1187 的 flow(15/20) 唯一红是 447-3，断言原文「测试库必须至少有一条打样申请，否则打印腿无从取证」，Expected 大于 0，Received 0。三条证据缺一不可。

一，该用例文件不在 1187 的改动面内，pulls/1187/files 的 17 个文件里没有任何 447 开头者，且该档在主干顶点上已存在。二，断言自身是夹具脆弱，main 版 447-3 只 GET 打样申请列表后断言长度大于 0，不自己造打样申请，本片库里没有别的用例留下的打样申请就必红。三，红只在 1187 出现是因为本片用例集变了：flow 分片按当轮用例全集做哈希均分，1187 新增六个 flow spec 共六千行以上，把 447-3 挪进了 shard0based=14 这一片；跨支检索证实其余四支的同名片段里根本没有 447，且它们的 flow(15/20) 全部 success，各支同名片段用例数也互不一致（64、66、63）。

可复用判据：判"某支红是不是它自己引入"时，除了比改动面，还要比该分片的用例集是否因本支新增用例而重排。分片重排会让一个与本支毫无关系的既有用例第一次在本支跑起来，看起来像本支引入，实则根因在主干侧的隐式夹具依赖。

## 结论九 更正结论八末句，flow17 与 flow20 是主干红不是各支自有红，解锁只能走甲案

结论八把 1182 的 flow17 与 1183 的 flow20 判为各支自有红，本轮取到断言原文后证伪。两枚 job 的失败用例是同一条，48-compensation-assertions.spec.ts 第 136 行的 48-2 O2C 全链，失败回显逐字相同，都是 POST /sales/orders/12/submit 返回 BUSINESS_ERROR 且文案为"客户状态为 inactive，不允许提交订单，请先将该客户恢复为启用状态"。

承载面逐枚取 blob 核实。48-compensation-assertions.spec.ts 与 91-ship-auto-ar-amounts.spec.ts 两枚都在主干上，主干 blob 分别是 db1b7346 与 5c5c3ee9。1182 头 1541df43a、1183 头 63340bb96、1184 头 c76157c93、1186 头 fddf150fb、1168 头 e795e5b38 五支全部逐字节等于主干 blob，只有 1188 头 9a5c084da 带修好的 dfc5cdf1 与 56be6249。所以这是主干红，修法已按"主线红必须收在同一支 PR"的裁定收在 1188，不是各支各自欠的债。

红位为何只在两支显形：分片按当轮用例集合哈希，各支用例集不同则 48-2 落进不同分片、与不同邻居并发，客户被别的用例置 inactive 的窗口只在部分分片成立。1184 与 1186 同轮没红不代表它们没有这条债，只代表那一轮没撞上。这与结论五的分片重排判据同源。

据此乙案（把修法 cherry-pick 扇出到四支）不成立：它会把同一笔主干红修法复制进五支，既违背主线红收一支的裁定，又会在 1188 合入后制造五处同文件冲突。正解只有甲案，且甲案的前置不是"用户拍板"而是"1188 全量面绿"。次序为 1188 绿后由用户在 UI 合入，随后先并基 1168（交集最多且 458 须按结论八合两侧修法），再按串行次序并基 1182 与 1183 与 1184 与 1186，每支并基后重推并等各自全量面绿。

并基时要分清两类文件。456 与 458 与 461 三枚主干不在册，是各支自带的重复份，取并集后的较新写法；48 与 91 两枚主干在册，1188 合入后直接取主干版即可，不要手工保留各支旧 blob。

## 结论十 参照面必须先 fetch 并核 behind 数，本轮差点据陈旧工作树写出三条假缺失

本轮做看板清理与功能缺口核实时，先在 repo1 工作树上 grep，得到 flow_card_material.rs 文件不存在、UNIT_KG 零命中、通知中心路由零命中、报价明细长度校验零命中四条结果。核 behind 数才发现本地 main 落后 origin/main 二十四笔（git rev-list --left-right --count origin/main...HEAD 输出 24 与 61，左为远端独有右为本地独有），目标文件根本不在本地册内，零命中是陈旧工作树造的假象不是真缺失。

fetch 后改以 origin/main 为参照面用 git grep 与 git ls-tree 重核，结果分成三类。第一类真缺失：idempotency_key 与 IdempotencyKey 在主干 backend/src 仍全仓零命中，D-53 的 HTTP 幂等重放防护确无承载，属乙类缺功能。第二类在途未进主干：flow_card_material.rs 不在主干树内且 UNIT_KG 零命中，说明台账记的 commit 0eff4268c（D-57 批次折平与 D-58 计量口径）在 1184 载体上，不是主干已修，看板对应任务需要保持开口到该支合入。第三类口径不足未判：通知中心路由与报价明细长度校验两条零命中所用的路径本身未核在册，按判据不能据单一口径零命中下结论，留待复核。

1. 461-04 报"付清后未付金额必须为 0.00 后端 Decimal 出参必须是字符串，实际类型=object 值={"v":"0","s":0}"。`{"v":..,"s":..}` 是本用例内定标值的内部表示形状，不是后端出参形状，被 expectDecEquals（其职责是解析原始出参并先钉线格式）当原始出参回喂即当场判红。修法是把该行改走已解析值对平口 expectDecMatch，提交 73dbc872f 与 863e2a419。同一文件内 expectDecimalString 与 expectDecMatchRaw 仍在逐字段钉"出参必须是 JSON 字符串"，线格式契约的覆盖面没有缩小，因此本改动不属放宽掩盖。
2. 456-05b 报"long filename must 4xx, actual 200"。真实契约是存盘名由服务端按 supplier 与 qualification 拼成受控形态，客户端原名只用于取扩展名，既不入库也不进路径，故长度不构成拒绝条件，上传应 200。两支载体各自把该腿改钉到这条真实契约（#1168 为 1e222f105，#1188 为 39a6b934a），断言方向一致（都断 200）。分歧只在覆盖面：#1168 多出列表回读、下载字节数与内容逐字节相等、删除后详情 404 三条腿，#1188 多出"原名不得进入存盘路径"与"出参任何字段不得回显原名"两条不泄漏断言。并档口径取两侧并集，以 #1168 为承载（456 属批次四测试面），#1188 的两条不泄漏断言按加严并入，不删任何一条。
3. 458-04 报 POST /inventory/transfers 得 BUSINESS_ERROR，与本轮第四处修法报的 quantity_available 恒 undefined 是同一档内两类不同破腿，均已由 #1188 修（e2096b593 与 293876d90）。四支带的是这两类修法之前的版本。

据此，四支的 flow(16/20) 不会因单纯并基而自解：并基只把主干内容换进来，三档在四支里是"本支新增文件"，与主干新增的同名文件构成 add/add 冲突，解法只有一种是取主干侧（即收敛后的版本）并把本支副本丢弃，四支对这三支文件没有任何本支自有改动值得保留（残量即历史快照）。这条并基解法与结论九的甲案次序一致：#1188 全绿并由用户合入后，#1168 先并基（458 取并集），再串行并基 #1182 #1183 #1184 #1186，每支并基后对这三支文件一律取主干版本。

判定器自证一枚：本轮取六支红面时先用自写的 board_all_open.mjs，六支齐报 total=0。真实原因是该脚本按裸数组取 /commits/{sha}/check-runs 的出参，而该端点出参是含 total_count 与 check_runs 两键的对象，取不到数组即静默判空，把取数失败读成"零格"。修法是显式取 check_runs 键并在首屏打 FETCH_BUG 哨兵，修后同一轮即得六支 73 或 90 格与四支三枚红名。另该轮四支红日志时间戳为 11-08，#1168 与 #1188 头为 11-09，比的是不同时点的跑次，不能据旧跑次判现头仍红。
