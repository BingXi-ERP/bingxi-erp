# 主干验证载体说明

本页只为解决一个事实：主干顶点的测试面被一次性合入后，这一批文件从未在 CI 上完整跑过。

## 为什么要开这一支

统一验证支（面料主链 400 到 454 共二十档加口令清理与幽灵清理腿）在合并请求的检查还只登记了两条、多数检查尚未物化的时候就被并入了主干。合入本身没有错，但它意味着：这二十个用例文件第一次被真实执行，是在之后任意一支的流水线里，而不是在它们自己的验证轮里。一旦其中有断言与后端契约不符，红会落在别人的分支上， attribution 会被推迟，排查要重新做一次。

按项目既有口径，PR 的检查是按当时的 base 跑的，背靠背合入互不验证；而主干自身的推送流水线只在版本标签上触发，分支推送不产生任何验证。所以验证主干现状的唯一办法，是从主干顶点拉一支载体分支，带上一个最小差异，让全量流水线在 merge ref 上完整跑一遍。

## 这一支带什么

只带本页。不改任何源码、不改任何用例、不动任何门禁配置。目的是取得一次主干顶点的完整检查结论，不做任何功能变更。

## 跑完之后要看什么

按 job 面逐档读，不读 run 级状态。重点三处：

1. 端到端分片作业里，400 到 454 这二十档是否有断言失败。失败先取断言原文，再对照本支改动面（本支改动面为零），据此判它是主干既有红而不是本支引入。
2. Rust 测试分片是否还有进程异常退出那一类，以及收尾汇总作业的红是否只是聚合结果而不是缺陷源。
3. 静态面：注释棘轮、路由快照、契约与信封检查这类本地镜像门在 CI 上的结论是否与本地一致。本地已验过端到端类型面在主干顶点等于基线，没有恶化。

结论出来后的处置次序：本支只负责产生结论，不负责修红。红按归属另开支修，测试面与功能面分支，避免同一轮里两种责任混在一起。
